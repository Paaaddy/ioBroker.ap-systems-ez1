## Problem Statement

The user owns an APsystems EZ1 microinverter and already maintains an ioBroker adapter (`ioBroker.ap-systems-ez1`, this repo) that polls the device's local HTTP API on port 8050. They want a small Android app as a parallel surface to the same inverter — a phone-native dashboard plus the two control affordances the device exposes (`setOnOff` and `setMaxPower`). The app is for personal use; ioBroker remains the system of record.

## What Makes This Cool

A self-contained Android app that talks directly to the inverter on the home Wi-Fi — no cloud, no vendor app, no ioBroker required. The whole thing is ~7 HTTP endpoints (already documented in `api/openapi.yaml`) and ships as a sideloaded APK from GitHub Releases. From "phone in pocket" to "inverter throttled to 600 W" is two taps. That's the whoa.

## Constraints

- **Local-network only** — the EZ1 has no remote/cloud API. Phone must be on the same LAN as the inverter (or a VPN to the LAN). This is acceptable for v1.
- **EZ1 Local Mode must be enabled** — the device's local API on port 8050 is gated by a "Local Mode" toggle inside APsystems' vendor app (AP EasyPower). The user must enable it once before the Android app can connect. The connect-failure error state must explicitly mention this.
- **One device per app instance** — the EZ1 API is single-device; no multi-inverter aggregation in v1.
- **Hardware safety** — writes (`setOnOff`, `setMaxPower`) must be fail-fast (no auto-retry), matching the existing adapter's behavior in `src/lib/ApSystemsEz1Client.ts`. A dropped write that the device silently applied could be double-applied by retry logic.
- **Cleartext HTTP** — the device speaks plain HTTP. Android API 28+ blocks cleartext by default. `network_security_config.xml` does **not** accept CIDR ranges (`<domain>` takes hostnames/IPs only), so the practical implementation is: (a) ship a `<base-config cleartextTrafficPermitted="false">` global default, and (b) at runtime, after the user enters an IP, build an OkHttp request that uses an explicit per-host `cleartextTrafficPermitted="true"` `<domain-config>` only for that one IP. Concretely: declare a `<domain-config cleartextTrafficPermitted="true">` block in the static XML enumerating the user's most-likely-needed gateway (e.g. `192.168.1.1`, `192.168.0.1`) plus a debug-only wildcard scoped to debug builds. For release builds, accept that this static-XML constraint means the user's inverter IP must fall within the enumerated set — document the supported IPs in the README, and provide a "rebuild from source if your inverter is on an unusual subnet" escape hatch. Do **not** set the global `usesCleartextTraffic="true"`.
- **No device-side write locking** — if both this app and a running ioBroker instance write at the same time, the device just applies whichever arrives last. Post-write verification is the only safety net. Acceptable for personal use; document the conflict surface.
- **Plaintext-on-LAN risk** — anyone on the same Wi-Fi can read or control the inverter via this API (no auth on the device). Out of scope to mitigate in v1; surface as a one-liner in the README.
- **No notifications, no charts, no multi-device in v1** — keep scope to "is it working right now and let me poke it." (Last-used IP is persisted; see Premise 5.)

## Premises

1. **Local-network-only is acceptable for v1.** No remote/cloud auth, no VPN setup baked into the app. User accepts that the app only works at home.
2. **No ioBroker dependency.** The app talks straight to the EZ1 HTTP API (`http://<ip>:8050`); it does not require ioBroker to be running.
3. **Sibling repo, not this repo.** Android code lives in a new repo (proposed: `apsystems-ez1-android`) separate from this Node.js adapter. Different toolchain, different release cadence.
4. **Read views + the same two writes the adapter exposes.** Dashboard for `getDeviceInfo` / `getOutputData` / `getAlarm` / `getOnOff` / `getMaxPower`, plus write buttons for `setOnOff` and `setMaxPower`. No history charts, push notifications, multi-device, or home-screen widgets in v1.
5. **Single persistence exception: the last-used inverter IP** is stored in DataStore (Preferences). Everything else is in-memory only.
6. **Polling cadence is decided, not open.** 5 s interval while the dashboard screen is foregrounded; no polling when the app is backgrounded or the screen is off. Single in-flight request at a time (Mutex-guarded).
7. **Confirmation on the off transition is decided, not open.** Tap-and-hold for 1 s on the on→off transition; instant on the off→on transition. `setMaxPower` writes >100 W away from the current cap also require a confirm dialog.

## Approaches Considered

### Approach A: Kotlin + Jetpack Compose, direct EZ1, sibling repo (RECOMMENDED)

- **Effort:** M (human ~1 weekend / CC ~3 hours).
- **Risk:** Low.
- **Pros:** Works without ioBroker. Single tech stack. Modern Compose UX. Smallest "complete" app that ships.
- **Cons:** Same-Wi-Fi requirement (no remote use). Some duplication of the adapter's request envelope and write-safety logic across TS and Kotlin codebases.
- **Reuses (conceptual, not literal):** the endpoint contract documented in `api/openapi.yaml`; the hardware-safety discipline encoded in `src/lib/ApSystemsEz1Client.ts` (read endpoints retry 3× with 100/200/400 ms backoff; write endpoints fail-fast with zero retries; `Math.round(watts)` before sending `setMaxPower` to avoid scientific-notation in the URL; mirror that encoding discipline in OkHttp's `HttpUrl.Builder`); the post-write verification pattern in `src/main.ts`.
- **Client implementation choice:** **hand-roll** the ~7-endpoint client in Kotlin (Ktor or OkHttp + Kotlinx Serialization). OpenAPI Generator's Kotlin output is rough — its handling of the EZ1's string-typed numeric/boolean fields is awkward, and the generator setup eats more time than the client itself for this surface size. A single sequential request via coroutines + Mutex replaces the TS client's `maxSockets: 1` discipline.

### Approach B: PWA wrapped as TWA, talks via ioBroker REST/Sockets

- **Effort:** S (human ~2 evenings / CC ~1.5 hours).
- **Risk:** Med.
- **Pros:** Smallest code. No Android Studio needed. iOS-friendly bonus. Inherits whatever ioBroker auth/remote access the user has already configured.
- **Cons:** Hard ioBroker dependency — if the broker is down, the app is dead. Two-hop latency (phone → ioBroker → device). PWA install/Trusted Web Activity UX on Android still feels second-class.
- **Reuses:** ioBroker REST/Web adapter API + this adapter's existing state tree directly.

### Approach C: Native Kotlin + Compose, dual-mode (direct + ioBroker fallback)

- **Effort:** L (human ~2 weekends / CC ~6 hours).
- **Risk:** Med.
- **Pros:** Best long-term — direct on home Wi-Fi (fast), ioBroker fallback when remote. Genuinely useful if the user ever leaves the house and wants to flip the inverter.
- **Cons:** Doubles the code paths for v1. Side-project completionist trap. Always reachable as a v2 upgrade from Approach A.
- **Reuses:** Same `api/openapi.yaml` + ioBroker REST.

## Recommended Approach

**Approach A — Kotlin + Compose, direct EZ1, sibling repo.**

Rationale: smallest thing that ships, matches the stated scope (dashboard + two controls) without overshooting it, and explicitly leaves the dual-mode upgrade path open as a clean v2. Ships a working artifact in a single weekend; the user can use it Sunday evening. Approach C's "remote access" benefit is hypothetical until someone is actually away from home and wants to throttle the inverter.

## UI States (per dashboard card)

Every card has **four lifecycle states** plus **one alarm overlay** that applies only to the Alarm card.

| Lifecycle state | Visual treatment |
|---|---|
| **Loading (first connect)** | Skeleton shimmer placeholder; dim card. |
| **Loaded (fresh)** | Normal card. Last-update timestamp at the bottom of the dashboard, not per card. |
| **Stale (poll failed once but still have last-known data)** | Card content remains visible, dimmed to 60 % opacity, "Stale" badge in the corner, last-update timestamp turns amber. |
| **Error (no last-known data)** | Card collapses to a single error line. Error copy is mapped from the failure type — see table below. Manual retry button at the dashboard level. |

**Alarm overlay (Alarm card only):** red border + filled red icon when any of `og` / `isce1` / `isce2` / `oe` is "Alarm". Composes on top of any of the four lifecycle states.

**Error-copy mapping** (so the user gets actionable copy, not a generic "Connection failed"):

| Failure type | Error copy |
|---|---|
| TCP connect refused, timeout, no route | "Can't reach the inverter. Check the IP, that you're on the same Wi-Fi, and that **Local Mode** is enabled in AP EasyPower." |
| HTTP-level error (4xx, 5xx, malformed body) | "Inverter responded but the API rejected the call. **Local Mode is probably off** — enable it in AP EasyPower." |
| Cellular-only network | "This app only works on Wi-Fi or VPN. Connect to your home network." (banner, not a card-level error) |

## Card Inventory (Compose dashboard)

Five cards in a single-column LazyColumn (one column on phones, two columns on tablets via `WindowSizeClass`):

1. **Power Card** (`getOutputData`) — large headline "Total: NNN W"; smaller subline "CH1: NNN W · CH2: NNN W".
2. **Energy Card** (`getOutputData`) — "Today: N.NN kWh" headline; "Lifetime: NN.NN kWh" subline; per-channel split as a tap-to-expand row.
3. **Alarm Card** (`getAlarm`) — four pills: Off-Grid, Short-Circuit-1, Short-Circuit-2, Output-Fault. Green when "Normal", red when "Alarm".
4. **On/Off Card** (`getOnOff` + `setOnOff`) — Switch component. Toggling on→off requires tap-and-hold for 1 s. Toggling off→on is instant. Loading spinner overlay during the verification window. **Encoding footgun:** the device's `setOnOff` query param is **inverted** (`status=0` = on, `status=1` = off). The Kotlin client must invert at the boundary so callers see normal boolean semantics.
5. **MaxPower Card** (`getMaxPower` + `setMaxPower`) — Slider clamped to `[minPower, maxPower]` from `getDeviceInfo`, discrete 10 W steps, current value shown numerically. Write fires **only on slider release** (not during drag). If `|new - current| > 100 W`, show a confirm dialog before sending.

## Post-Write Verification (pseudocode)

For both writes — applies on a coroutine, never blocks the UI thread:

```kotlin
suspend fun writeAndVerify(
    desired: T,            // the boolean for setOnOff or the Int watts for setMaxPower
    write: suspend () -> Unit,
    read: suspend () -> T,
    matches: (actual: T) -> Boolean,
): VerifyResult {
    // 1. Optimistic UI update happens BEFORE this call
    write()                     // fail-fast: 0 retries (matches ioBroker client)
    delay(2_000)                // give the device time to apply
    val actual = read()         // read endpoint: 3 retries with 100/200/400 ms backoff
    return if (matches(actual)) VerifyResult.Ok
           else VerifyResult.Mismatch(actual)
           // UI: revert optimistic state, mark connection unhealthy
}
```

- Verification window: **2 s** wait before the read, matching the ioBroker adapter (`src/main.ts`).
- "Matches" semantics — `setOnOff`: exact boolean equality. `setMaxPower`: `actual == round(desired)`. The slider already clamps `desired` into the device-reported `[minPower, maxPower]` range, so a mismatch here is a **genuine error** (device rejected the value or comms dropped), not silent device-side clamping. No tolerance window needed.
- During the verification window the UI shows a small "Verifying…" indicator on the affected card. The control itself is disabled. This is **not** a 2 s freeze of the whole app.
- On `Mismatch`, revert the optimistic state, surface a non-blocking snackbar ("Device didn't accept the change"), and treat the connection as unhealthy until the next successful poll.

## Open Questions

1. **Device discovery vs. manual IP entry?** v1 is decided: single text field, last-used IP persisted in DataStore. mDNS/SSDP discovery is v2.
2. **Min Android API level?** Suggest API 26 (Android 8.0) as the floor — covers ~98% of devices, lets Compose use modern features without compat shims. **Decision needed before bootstrap.**
3. **License / open-source release?** This adapter is MIT. Suggest the same for the sibling Android repo unless the user wants different.
4. **DHCP IP changes** — when the inverter's IP changes, the app surfaces the standard error state (see UI States) and the user re-enters the IP. mDNS rediscovery is v2. Acceptable for v1 because home routers usually give the same IP back.
5. **Wi-Fi-vs-cellular preflight** — use `ConnectivityManager.activeNetwork` + `NetworkCapabilities` to detect cellular-only and show a "this app only works on Wi-Fi or VPN" banner instead of letting the connection hang. Treat the connection as OK if any of `TRANSPORT_WIFI`, `TRANSPORT_VPN`, or `TRANSPORT_ETHERNET` is present (VPN-over-cellular is a valid path to the home LAN). Requires `<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />` in the manifest. **Confirm this UX is acceptable.**

## Success Criteria

- App installs from a signed `.apk` artifact built by GitHub Actions on the sibling repo's release tag.
- On first launch, the IP-entry screen accepts an IPv4 address; on subsequent launches it pre-fills the last-used IP from DataStore.
- Pressing "Connect" loads `getDeviceInfo` + `getOutputData` within 2 seconds on home Wi-Fi.
- Dashboard renders the five cards (Power, Energy, Alarm, On/Off, MaxPower) with all four UI states correctly handled (loading skeleton, fresh, stale-with-badge, error).
- All numeric/boolean fields returned as strings by the device (`minPower`, `maxPower`, `status`, alarm flags `og`/`isce1`/`isce2`/`oe`) are parsed at the client boundary into `Int` and `Boolean` types; UI never sees the raw string.
- Foreground polling cadence is 5 s; backgrounding the app cancels the polling job (verifiable via `adb shell dumpsys` or by observing no network traffic when screen is off).
- `setOnOff` toggle works with the inverted device encoding hidden behind the client (`status=0` = on, `status=1` = off); on→off requires 1 s tap-and-hold; UI shows "Verifying…" during the 2 s window without freezing.
- `setMaxPower` slider clamps to device-reported `[minPower, maxPower]`, writes only on release, prompts a confirm dialog on deltas >100 W.
- Post-write verification reverts the optimistic UI on mismatch and surfaces a snackbar.
- Cellular-only network state shows a non-dismissable banner; the connect button is disabled. `TRANSPORT_VPN` and `TRANSPORT_ETHERNET` count as OK.
- Concurrent writes (e.g. fat-fingering the on/off toggle while dragging the MaxPower slider) result in **serialized** HTTP requests on the wire, not interleaved — verifiable by capturing traffic with Charles or mitmproxy and confirming sequential request/response pairs.
- An overflow / settings menu exposes a **"Change inverter IP"** affordance so DHCP IP changes don't require uninstall/reinstall.
- Done = on real hardware, the user can launch the app, connect to the inverter on home Wi-Fi, toggle off→on, and adjust `MaxPower` once without a crash and with all writes verifying successfully.

## Distribution Plan

- **Sibling GitHub repo:** `Paaaddy/apsystems-ez1-android` (or similar). MIT license to match this repo.
- **CI/CD:** GitHub Actions workflow — debug APK on every push, signed release APK on tag push (`v*.*.*`), artifact attached to GitHub Releases. Checkout step **must** use `actions/checkout@v4` with `fetch-depth: 0` so `git rev-list --count HEAD` works (Actions defaults to depth=1, which would always return 1).
- **Install path for users:** Download `.apk` from Releases, sideload. Realistic flow on Android 12+: tap APK in Files app → grant "Install unknown apps" for the Files app → Play Protect warning appears → tap "Install anyway" → "Open". That's 3-5 taps the first time, ~2 on subsequent installs. Document this in the new repo's README so the install isn't framed as one-tap.
- **Versioning:** `versionCode` from `git rev-list --count HEAD` (requires `fetch-depth: 0`); `versionName` from the latest tag (`git describe --tags`). Alternative if shallow-clone hygiene becomes a problem: `github.run_number` for `versionCode`.
- **Signing — concrete checklist (this is ~half a day of work, not a footnote):**
  1. `keytool -genkeypair -alias upload -keyalg RSA -keysize 2048 -validity 10000 -keystore upload.jks` — generate locally.
  2. `base64 -w0 upload.jks > upload.jks.b64` — encode for the secret.
  3. Store four GitHub Actions secrets: `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.
  4. In the workflow, decode the keystore and export its path so Gradle can find it:
     ```yaml
     - run: echo "$ANDROID_KEYSTORE_BASE64" | base64 -d > $RUNNER_TEMP/upload.jks
     - run: echo "KEYSTORE_PATH=$RUNNER_TEMP/upload.jks" >> $GITHUB_ENV
     ```
  5. In `app/build.gradle.kts`: `signingConfigs { release { storeFile = file(System.getenv("KEYSTORE_PATH")!!) ; storePassword = System.getenv("ANDROID_KEYSTORE_PASSWORD") ; keyAlias = System.getenv("ANDROID_KEY_ALIAS") ; keyPassword = System.getenv("ANDROID_KEY_PASSWORD") } }` and reference it in `buildTypes.release`.
  6. **Back up** `upload.jks` somewhere safe (1Password, encrypted USB) — losing it means losing the ability to publish updates to the same install.

## C. Premise patches (CEO D2.2 + Eng D5.1 — CONFIRMED across both reviewers)

**Premise 3 (sibling repo) — patched, not replaced.** The sibling-repo decision stands, but the openapi-spec drift risk between this Node.js repo and the new Android repo is real. **Required mitigation:** the Android repo vendors a copy of `api/openapi.yaml` and ships a `scripts/sync-openapi.sh` that `curl`s the raw YAML from this repo and `diff`s. CI runs this on every push and fails the build if the vendored copy is stale. A scheduled (weekly) GitHub Actions job opens a PR when upstream drifts. Lowest-friction option for a side project.

**Premise 8 (new) — Cleartext-HTTP trust is per-host, runtime, not static-XML.** (CEO D2.4 + Eng D5.2 — CONFIRMED.) Replace the "enumerate gateway IPs in `network_security_config.xml`" approach with a runtime per-host trust mechanism. Concretely: keep `<base-config cleartextTrafficPermitted="false">` as the global default, then build the OkHttp client for the EZ1 host with `connectionSpecs(listOf(ConnectionSpec.CLEARTEXT))`. This grants cleartext to that one client instance, irrespective of `network_security_config.xml`, and works for any user-entered IP without rebuild-from-source. The static-XML enumeration approach is removed.

## D. Architecture patches (Eng phase)

- **Polling owner:** the polling job lives in the `DashboardViewModel`'s `viewModelScope`, started/stopped via `repeatOnLifecycle(STARTED) { while (isActive) { poll(); delay(5_000) } }` in a `LaunchedEffect`. Not `GlobalScope`, not `Application`-scoped.
- **Write-vs-poll serialization:** writes preempt polls. Implement as a single-worker `Channel<Command>` consumed by a coroutine — write commands cancel any in-flight poll (`pollJob?.cancelAndJoin()`) before running. Polls are paused for the entire `writeAndVerify` window (write + 2 s + verify-read). A generation counter on the ViewModel state drops late poll results that arrive after a write has updated state.
- **OkHttpClient discipline:** singleton (`object` or DI). `ConnectionPool(maxIdleConnections=1, keepAliveDuration=60, SECONDS)`. `dispatcher.maxRequestsPerHost = 1`. Timeouts: `connectTimeout=2s, readTimeout=5s, writeTimeout=5s, callTimeout=8s`. `retryOnConnectionFailure(true)` on read-only client; the write client uses a separate instance with `retryOnConnectionFailure(false)` to preserve the no-retry contract.
- **Wi-Fi roam handling:** register a `ConnectivityManager.NetworkCallback`; on `onLost` and `onAvailable` call `okHttpClient.connectionPool.evictAll()` to drop stale sockets bound to the previous AP.
- **Malformed-JSON handling:** the EZ1 firmware occasionally returns 200 with truncated JSON. Catch `kotlinx.serialization.SerializationException` separately from HTTP-level errors and treat it as a transient retryable read error (covered by the existing 3× backoff). Do NOT surface it as "Local Mode is probably off."
- **DataStore IO:** all reads/writes on `Dispatchers.IO`.
- **State shape:** five `StateFlow<CardState<T>>` per card (Power, Energy, Alarm, OnOff, MaxPower) collected via `collectAsStateWithLifecycle()`. This avoids whole-tree recomposition every 5 s. Acceptable alternative: one `StateFlow<DashboardState>` + `derivedStateOf { state.power }` per card.

## E. UI patches (Design phase)

- **Status header (Design D1).** Pin a one-line status header above the LazyColumn: "Producing 412 W" or "Idle" or "Off" or "Alarm — see below" — synthesized from On/Off + Power + Alarm. This is the answer to "is it on and making power right now" and must be the visually largest text on the dashboard.
- **Card subtraction (Design D4) — APPROVED at Phase 4 Gate (2026-05-05).** Dashboard reduces from 5 cards to 3:
  - **Production card** (merges Power + Energy from `getOutputData`) — headline current W, secondary today/lifetime kWh, expandable per-channel breakdown for current W only (drop per-channel Energy split entirely in v1).
  - **On/Off card** (`getOnOff` + `setOnOff`).
  - **MaxPower card** (`getMaxPower` + `setMaxPower`).
  - **Alarm** is no longer a card — rendered as a thin inline banner above the cards, present only when one or more flags is raised. A small check icon in the top app bar indicates "All systems normal" otherwise.
  - Card order: Production, On/Off, MaxPower (controls follow status; both controls above the fold on a phone screen without scrolling).
  - Typography scale (revised for 3-card layout): Status header 48sp · Production-card "current W" 36sp · card titles 20sp · sublines 14sp.
- **First-launch + IP-entry state.** Connect button disabled until a valid IPv4 has been typed; inline validation error on invalid input; placeholder text "192.168.1.x". DataStore-backed last-IP pre-fills on subsequent launches.
- **Rotation / process-death mid-write.** Hoist the `writeAndVerify` job to `viewModelScope` keyed by `SavedStateHandle` so a config change re-attaches to the in-flight verification rather than restarting it.
- **Stop optimistic UI on writes (Design D5 critical).** Do NOT optimistic-update the UI before verification. Instead: when the user toggles the Switch, render an indeterminate "Switching on…" / "Switching off…" state on the control (disabled, animated). Only commit to the new visual state on verified success. This eliminates the 2 s window where the UI lies about device state.
- **Hold-to-off discoverability (Design D6 critical).**
  - Visual: circular progress arc around the Switch thumb fills 0 → 360° over 1 s; release before completion cancels and resets.
  - Haptic: tick at hold start, confirm at completion.
  - Discoverability: first-launch one-time tooltip "Hold to turn off" anchored to the Switch.
  - On a too-short tap during the off transition, show a transient "Keep holding…" label.
- **Slider polish.**

## F. Test pyramid (Eng D3 — required before first sideload)

- **Client unit tests (MockWebServer):**
  - `setOnOff(true)` issues `?status=0`; `setOnOff(false)` issues `?status=1` — encoding inversion.
  - `setMaxPower(500.7)` issues `?p=501` — float rounding.
  - Read endpoint retries exactly 3 times on `IOException` with 100/200/400 ms backoff (use `MockWebServer` + `SocketPolicy.DISCONNECT_AT_START`).
  - Write endpoint retries exactly 0 times.
  - 200 + malformed JSON surfaces as `SerializationException`, not generic HTTP error.
  - String-typed numeric/boolean fields (`minPower`, `maxPower`, `og`, `isce1`, `isce2`, `oe`, `status`) parse to typed values.

- **Skip in v1:** Compose UI tests — covered by manual visual QA on the actual device.
- **CI:** `./gradlew test` runs in the GitHub Actions workflow before the APK build step; build fails on test failure.
